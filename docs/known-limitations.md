# Known limitations

What the guards do not cover. Moved from the README.

These guards are defense-in-depth, not a security boundary. Be clear-eyed about what they do **not** cover:

- **Guard hardening is frozen as of 2026-11-15** ([#237](https://github.com/AdityaRon/claude-code-harness/issues/237)). No more lexer or bypass work goes into the regex guards: a way past one is a known limitation, not a bug to fix. The OS sandbox is the containment; `bin/sandbox-trial.sh` reports what works under it.
- **Regex guards have a ceiling.** Command-string matching can always be evaded by a determined agent (string-obfuscated interpreter payloads, novel tool invocations, multi-step stage-then-exfil across separate commands). The guards raise the bar and catch the obvious/accidental cases; the **OS sandbox** is the only real containment for the evasion class. See [customization.md](customization.md#os-sandbox).
  - `kubectl-guard` puts in place what the command itself sets (`k=kubectl; "$k" delete`, `${KUBECTL:-kubectl}`, `$(which kubectl)`, `for k in kubectl`) and asks when xargs, a substitution or an unset variable supplies the verb or `get`'s kind. A name it cannot see is out of reach, because the command never spells `kubectl`: a profile alias or function (`k delete pod x`), a variable exported by an earlier command, a spliced name (`kube$x`), or text a substitution transforms (`$(sed … <<< kubectl)`). So is a name set by something other than an assignment or a `for` list (`printf -v c kubectl`, `read c <<< kubectl`, `${!ref}`), and xargs behind a wrapper (`env xargs kubectl`). A `describe` kind from a substitution is not asked about either: describe prints a Secret's key names, not its values. The other way round, `… -o name | while read p; do kubectl get $p; done` asks although the names are pods: the guard reads a loop's list or the segment before xargs, not what a `while read` takes from a pipe. An inline script's shell-outs are read, but not a script file (`python3 x.py`), a heredoc under a wrapper (`uv run python - <<EOF`, `env python3 - <<EOF`; the `-c` forms are read), `cat <<EOF | python3`, ruby or perl `qx` with other delimiters, php's `shell_exec` and `passthru`, or a command a script assembles across statements (that asks only when the script names `kubectl`).
  - `config-guard` resolves a symlink only in a command it reads in full, and it leaves early on a command that names none of its paths. So a link into `~/.claude/hooks` made with a relative target (`ln -s ../../Users/me/.claude/hooks /tmp/h`, which the guard resolves from the session's folder and so does not ask about) is written through unasked by a later `echo x > /tmp/h/lib.sh`: two steps, neither stopped. The same holds for a link inside a job's scratch folder (`~/.claude/jobs/<id>/tmp`), `~/.claude/projects` or `~/.claude/logs`: a command that names `.claude` only through one of those three is no longer read in full, because 3,677 of the 6,155 commands that reached the full check on one Mac did so for those paths alone (14,155 Bash calls in 30 days of transcripts, run through the filter before and after, 2026-11-16). A command with `..` in it, a case variant (`~/.CLAUDE/…`) and any other `.claude` path are read as before.
  - `git-guard` asks when a variable, a substitution or a function's arguments supply git's subcommand, but like `kubectl-guard` it cannot see a git the command never spells: a profile alias or function (`g push --force`), or git run by a script file.
  - `kubectl-guard`, `git-guard` and `rm-guard` read an inline script's shell-outs; `env-guard` and `network-guard` do not. So `python3 -c "import os; os.system('cat .env')"` gets an ask from `interpreter-guard` where the typed `cat .env` is denied, and a `curl … | sh` inside one gets an ask from `network-guard` where the typed form is denied. Python's own file and network calls (`shutil.rmtree`, `open('.env')`, `urllib`) are not shell-outs and no guard here reads them as such; `interpreter-guard` asks on the dotfile and socket ones.
  - A heredoc body written to a prose file (`cat > n.md <<'EOF'`) is not scanned by `env-guard`, `git-guard`, `interpreter-guard`, `kubectl-guard` or `network-guard` when every other command in the call is an inert reader or writer (`strip_inert_heredocs`). `echo` is inert whatever its arguments, so `cat > n.md <<'EOF'` … `EOF; echo $(bash n.md)` runs the body unscanned. Low severity: a file the Write tool writes, then runs, is not scanned either.
  - A false positive: a body no shell reads is also read the way a script run later would read it, with a quote carried across its lines, and those lines are scanned as code after the command. A python heredoc with `m = 'it\'s'` (an open quote to the shell) and then `assert s==set(p)|r, (set(p)|r)-s` is denied by `env-guard`, which reads `set` there. Run the body from a file instead (`python3 -I f.py`); the deny's reason says so when the command holds an interpreter heredoc.
  - Same on main and not fixed, since the #237 freeze holds new deny coverage until the 2026-11-29 review:
    - A `cd "$CLAUDE_JOB_DIR/tmp"` line in a notes body, which never runs, moves `rm-guard`'s base into scratch, so a later `rm -rf build` in the session's folder is allowed.
    - `rm-guard`'s full read takes `r\m -rf ~/` for another word, and reads an inline script's shell-out only in lower case (`subprocess.run(['RM','-rf','/'])`), and allows both, so its filter, which now passes them on, does too. `RM`, `Rm` and `r''m` deny as `rm` does (macOS's disk runs `RM` as `rm`).
    - A script written and sourced in one command (`cat > ~/n.sh <<EOF` … `cd .claude` … `EOF`, then `cd ~ && source n.sh && echo x > statusline.sh`): `config-guard` does not follow the script's own `cd`, and bash writes `~/.claude/statusline.sh` unasked.
    - A script body's `(cat .env)`, then `bash x.sh`, is allowed by `env-guard`: a body's parens are data.
    - `os.system('set | head')` in a python heredoc is allowed, with or without an apostrophe line before it: `env-guard` does not read shell-outs (above), and `interpreter-guard` does not ask on it.
    - A git force push assembled inside an interpreter from adjacent string literals (python's `'git pu' 'sh --force origin main'`) or a perl or php `.` join is allowed by `git-guard`; a `+` join (python, node, ruby, bun) is rebuilt and caught.
    - `config-guard` does not resolve a variable the command sets (`d=.claude; cp x ~/$d/settings.json`), a brace (`~/.{claude,x}/settings.json`), a glob in a folder above the file under `~/Library` (`~/Library/Launch*/x.plist`; a glob as the last name asks), a split option (`git config --glo"bal"`) or a glob after a `cd` (`cd ~ && echo x >> .*rc` run from another folder: the glob is expanded from the session's folder). Nor does it read a glob in the folder a `cd` enters (`cd ~/.cla* && cp x settings.json`), a `>&` with a path after it (`echo x >&~/.bashrc`), a quote inside `[ ]` (`~/.cl[a" "]ude`), `$'...'` in a name (`~/.cl$'a'ude`), a quoted option (`git config "--global"`) or a glob in `Library` (`~/Libr?ry/LaunchAgents`). Its full read allows each, so its filter does too. A path split by quotes or a backslash (`~/.cl''aude/hooks/lib.sh`), a glob in a dot-name (`~/.cla*/settings.json`), and one after `//`, `/./`, `/DIR/../`, the home path typed out or `./` from home (`~/.config/../.?ashrc`) ask.
- **Auto mode hands the unasked middle to a model.** Guard asks still come to you, but everything no guard or rule names is approved or blocked by the classifier, by judgment rather than by rule. See [auto-mode.md](auto-mode.md). Set `defaultMode` to `manual` to see every one of those yourself.
- **MCP connectors are logged, not guarded.** `network-guard` sees Bash `curl`/`wget` (not `WebFetch`, whose ask went in #237), but MCP tools (Gmail, Google Drive, Slack, Atlassian, browser automation, …) can read files and send data outbound with no guard in the middle. Since the `mcp__.*` audit row in [hooks.md](hooks.md), every such call leaves a line naming the tool and its field names, which is a record after the fact rather than a stop before it. Control the surface by only connecting MCP servers you trust, and use the log to decide which of them deserve a real guard.
- **A Claude Code mod can override the guards.** Mods (2.1.287+) are plugin code that runs inside Claude Code. Per the [permissions docs](https://code.claude.com/docs/en/permissions#extend-permissions-with-hooks), a mod can approve a call a guard here blocked, or answer a call itself so the guards never run. Unless the machine has managed settings or a Team/Enterprise login, it can also approve a call a `deny` rule refuses. `syncClaudeAiPlugins: false` closes the synced route only. What the harness does instead:
  - **Claude can write you mods, reviewed.** `mod-gate` runs `claude plugin validate` (the static analysis Claude Code loads mods by) on each mod file Claude writes, as the mod will be after the write. It denies the hooks that replace permission decisions (`tool.check`, `classic.PreToolUse`, `classic.PermissionRequest`, `plugin.register`, `engine.create`) and shows you everything else the mod hooks and calls in a notice, flagging `tool.call` and calls that run outside the guards (`$.process`, `$.http`, `$.fs.write`, …); since #237 that notice no longer asks. In auto mode the write itself goes to the classifier, and since Claude Code 2.1.321 a mod Claude writes loads in auto and bypass modes with no hot-reload prompt (its changelog), so that notice is where you see what the mod does. A write from Bash into such a mod (the session's `~/.claude/dev-mods` folder, or a mod under a `.claude/skills` folder, found by its nearest manifest as `mod-gate` finds it) never reaches `mod-gate`, so `config-guard` asks before it; `cd` into the mod and a relative write count. On resume, `session-start` names any mod the session wrote, since one declined with "Not now" loads then.
  - **Third-party plugins stay yours to install.** Deny rules stop Claude running `claude plugin install`/`enable`/`update`/`marketplace add` or `--plugin-url`, and editing the installed-plugin cache `~/.claude/plugins` with the file tools or a redirect; `config-guard` asks before any other write there from Bash (`cp`, `tee`, `mv`). `/plugin install` from your own prompt is unaffected.
  - **Not covered:** a mod written from inside an interpreter (`python3 -c`, a script file), into a `--plugin-dir` folder outside `.claude`, or copied whole into a new `.claude/skills/<name>` (`cp -R`, which has no manifest there yet), a `CLAUDE_CODE_PLUGIN_DIRS` prefix, and a `tool.call` hook that answers calls (shown, not blocked: static analysis can't tell it from a counter). The harness ships no managed settings on purpose: they would collide with a work machine's own, and the setting that blocks sideloading also blocks `--agents` and `--mcp-config`.
- **Guards fail *closed* without jq**, so a missing-jq machine blocks all Bash/file tool calls rather than allowing them unchecked. Keep `jq` installed (the installer checks for it). They fail closed on input jq cannot parse too: a truncated or non-JSON payload is denied rather than read as an empty command. An absent or empty *field* on parseable input is a different case and still passes, since every guard is registered on tools it does not inspect.
- **A background session loses `~/Desktop`, `~/Documents` and `~/Downloads` after a Claude Code upgrade.** macOS keys those grants to the binary's path when the session host is its own responsible process (`claude --bg-pty-host` under launchd; the TCC log on 2026-10-22 shows `identifier_type=Path`), and a Homebrew or native upgrade deletes that path while the host runs on. The grant stops matching when tccd next restarts (idle-exit, 2 h 15 min after the upgrade in that log), and every access there fails with `Operation not permitted` until the host is restarted; a session under a terminal app rides the app's grant and is unaffected.
  - `session-start` and `tcc-check` name the deleted binary and the fix; `bash doctor.sh --hosts` lists every such process; `harness-update.sh` names the processes it is about to cut off and records the upgrade in `~/.claude/state/cli-upgraded`.
  - The end of it is a clone outside those folders: `bin/relocate-clones.sh` (installed as `~/.claude/relocate-clones.sh`) moves one, repairs its worktrees and renames its `~/.claude/projects` records.
- **A guard that crashes or times out blocks the call.** Each one carries `"onFailure": "block"` (Claude Code 2.1.295 and later); without it Claude Code runs the call unchecked. 2.1.292 ignores the key and the guard still works. `bash-guards` carries `"timeout": 60`; the other guards keep Claude Code's default of ten minutes, where they take well under a second.
  - The seven Bash guards run inside one hook, `bash-guards`. A guard that dies there is a deny naming it, and an early exit of `bash-guards` itself (a failed `source`, an `exit 1`) is made exit 2, a block on every version. A signal is not: TERM, HUP and INT end it with their own status (143, 129, 130) and SIGKILL runs nothing. From 2.1.295 `onFailure` blocks those; on an older CLI each is a non-blocking error, so the call goes on unchecked by all seven, where seven hooks lost one.
  - Inside `bash-guards`, a guard that has not answered 45 s after the hook started (`CLAUDE_GUARD_DEADLINE`) is a deny naming it, and its process group is killed. The 60 s timeout is the backstop: when Claude Code's timeout fires it drops the hook's output, and its message names no guard. `read -t` takes whole seconds on bash 3.2, so the deadline fires between 44 and 45 s, and each further late guard adds up to a second.
  - A guard runs on to its end when its fork is killed by SIGKILL with no TERM first, since the fork's trap is what kills the guard's group. TERM, HUP or INT to the hook, or HUP to its process group, stops every guard. What Claude Code sends a hook on Esc is untested.
  - The deadline is wall time. On macOS a call the machine slept through is waited for again from the wake (`kern.waketime`), once, and that second wait can outlast Claude Code's 60 s if the call had run long before the sleep. Linux has no check as cheap, so there a call that spans a suspend can be denied on resume.
- **A subagent is stopped between calls, not paused.** `subagent-cache-guard` can only deny an agent's next tool call; a call already under way finishes and pays its rewrite, and an agent that makes no tool calls is never counted. The gap is wall-clock time between tool calls, so a single tool that runs past the TTL (a long test run) counts as one too, which it is: the next call misses the cache either way. Nothing writes the agent's state to disk; its reply is the checkpoint, and the parent resumes it with SendMessage. An in-process teammate carries `agent_id` too (hooks reference); whether Claude Code fires SubagentStop when one goes idle is untested, and if it does not, a teammate's idle gaps count like a sleep. Set `CLAUDE_SUBAGENT_MAX_COLD_STARTS=0` for an agent team.
- **What `disk-space.py` deletes, and what it cannot see.** `prune`, `clone` and `bazel --sweep` delete only by digest, behind ask rules and an `rm-guard` ask, and keep anything a git repo holds that no remote has. Outside what they check:
  - Commits only a reflog holds (an amended or reset branch's old tip) are not looked for, and go with the clone.
  - A filter set in a repo's own config, or a file that config includes, keeps the repo unjudged, since `git status` would run it. One in system or global config (`git-lfs`'s) is yours and runs, as on any `git status` in that repo.
  - A clone holding a linked worktree of itself is kept once quarantined, since git records the worktree by its absolute path; `git worktree remove` it first.
  - An output base whose workspace sits on a mount that is not mounted counts as `unknown` only under `/Volumes/<name>`. A workspace under an empty mount point elsewhere (Linux `/mnt/x`) counts as gone, so `bazel --sweep` may list its base.
  - A `DO_NOT_BUILD_HERE` holding any whitespace past one trailing newline names an `unknown` workspace, so its base is never swept. That includes a workspace path with a space in it.
  - A global `[include]` whose absolute path points into a clone makes git run that clone's filter during the listing, as any `git status` there already would.
  - An apply stopped by TERM, HUP or Ctrl-C puts the entry it holds back under its name. One stopped harder (`kill -9`, a crash) leaves it as `.disk-space-quarantine-<pid>-<hex>-<name>`. Each listing names such an entry, with the `mv` that restores it, and never deletes it.
  - `prune --now EPOCH` moves the time ages count from, for tests. Which jobs are live still goes by the clock.
